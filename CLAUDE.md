## What this is

The `gh-pages` branch of `wr/enshittifier`, served at <https://enshittifier.wells.ee> via GitHub Pages (Cloudflare-proxied). Two distinct things live here:

1. **Marketing site** — `index.html`, `privacy.html`, `404.html`, `style.css`, `og-image.png`, `fart.mp3`. Static; no build, no tests, no runtime deps. To preview, run `python3 -m http.server` in the repo root.
2. **Sparkle update feed** — `appcast.xml`. **Do not hand-edit.** It's overwritten on every release by the Mac-app `scripts/release.sh` on `main`, which pushes the updated feed here. If you need to change feed format/structure, edit the template in the release script on `main`, not the generated XML here.

The Mac app source lives on the `main` branch (sibling worktree at `../enshittifier`). The Chrome extension is a separate repo entirely (`wr/enshittifier-extension`).

## The toggle

The fixed top-right AI/💩 switch is the centerpiece. It's a single button with two visible halves and a thumb that slides between them — clicking either side flips the page via `[data-mode="poop"]` on `<html>`, which CSS-cascades to every `.swap`/`.d-swap` instance in the prose and demo card. State persists in `localStorage` (`enshittify-on`). On flip, a 175 ms `fart.mp3` is played back through a Web Audio `AudioBufferSource` with a randomized 0.86–1.20× `playbackRate` so repeated clicks layer naturally instead of sounding identical. The inactive side beckon-pulses (scale 1→1.16, 2.4s loop) until the user has touched the switch once.

## Cache busting

Cloudflare caches static assets aggressively (4h default). When you ship a CSS or JS change, bump the `?v=N` query in the `<link rel="stylesheet" href="style.css?v=N">` tag of every HTML file so the new asset bypasses the stale cache entry. The MCP token in this workspace can't `Cache Purge` — bumping the query string is the canonical workaround.

## Pre-publish checks

`./scripts/check.sh` runs the full suite. Each sub-check in `scripts/checks/*.sh` is independently runnable. Brew-installed tools listed in `Brewfile` (`lychee`, `oxipng`, `jpegoptim`, `svgo`, `gifsicle`, `node`); npm dev-deps in `package.json` (`htmlhint`, `stylelint`, `lighthouse`). Run `brew bundle && npm install` once, then `./scripts/install-hooks.sh` to wire the pre-push hook into `.git/hooks/`.

What each check does:
- **images** — auto-compress every tracked image (PNG/JPG/SVG/GIF) via the brew tools. Stages the result. `--ci` reports without modifying.
- **lint** — htmlhint over each `*.html`; stylelint over `style.css`. (No standalone JS — the toggle code is inlined in `index.html`.)
- **meta** — required `<title>`, `<meta description>`, og:*, twitter:card. Length bounds. og-image.png dimensions ~1200×630.
- **links** — spins up `python3 -m http.server` on 8766; lychee walks every link, internal + external. `--no-external` keeps it offline.
- **lighthouse** — mobile + desktop, gated on performance/SEO/a11y/best-practices floors (currently perf ≥ 70, seo ≥ 95, others ≥ 90). Tighten as the site improves.

The pre-push hook only fires for pushes to `refs/heads/gh-pages` and skips when the only diff is `appcast.xml` (the release script's autogenerated feed). Bypass any check with `git push --no-verify`.

## Release / deploy

Pushing to `gh-pages` kicks the `pages.yml` workflow on `main`, which uploads the branch contents as a Pages artifact. Custom domain `enshittifier.wells.ee` is fronted by Cloudflare (proxied A record on the wells.ee zone). HTML is `cf-cache-status: DYNAMIC` (not edge-cached); CSS/JS/PNG/MP3 get 4h Cloudflare cache, hence the `?v=N` busters.

Use `./scripts/publish.sh` instead of `git push origin gh-pages` — it forwards every flag to `git push` but filters out GitHub's reflex "Create a pull request for 'gh-pages' on GitHub by visiting…" sideband (there's no server-side opt-out, so it has to be grepped at the client). The pre-push hook still fires.

`gh-pages` is intentionally a **single-commit history** — every meaningful push is squashed back to one orphan "Initial commit" so the branch stays cheap to clone and the log has no churn. Treat it as a deploy target, not a source-of-truth history; the source-of-truth for the site is the working tree.
